# i18n Display Bugs & the Global `t` Naming Conflict

Read this before touching `window.t()` / `window.tFormat()` calls, `data-i18n`
attributes, or anything that renders a translated label from JavaScript.
Cross-cutting loader rules (attributes, interpolation, cache busting) stay in
[AGENTS.md](../../AGENTS.md#-localization-i18njs).

## The loader in one paragraph

`js/i18n.js` defines `window.t(key, defaultText)` **synchronously** and returns
`defaultText || key`. `window.rekindleTranslations` only fills in after the async
`fetch('locales/<lang>.json')` resolves, and it fires
`document.addEventListener('rekindle:i18n:ready')` when it does. **For
`lang === 'en'` with no `data-i18n-file`, the fetch is skipped entirely** (the
loader sets `files.length = 0`) because every `data-i18n` element already carries
English copy in the markup. So in English, `window.t('some.key')` with no
fallback returns the raw key *by design*, not as a race condition.

## The three display bugs

### 1. Raw key shown (`blackjack.label.bank`, `hangman.status.guess`, …)

`window.t('some.key')` called **without a fallback** returns `defaultText || key`,
i.e. the **raw key string**. If the code then also does
`removeAttribute('data-i18n')` (a common pattern to stop the loader overwriting
dynamic text), the raw key is stuck on screen permanently.

**Fix:** always pass an English fallback as the second argument, or use
`tFormat`. The 2026-10 codemod added fallbacks to every *literal*
`window.t('key')` call in the repo; keep it that way.

### 2. Raw `${placeholder}` shown (`MODE: ${NUM}`, `Mode: ${mode}`)

Never put `data-i18n="key"` on an element whose locale value contains `${...}`
placeholders — `applyTranslations()` sets `innerText` to the **uninterpolated
template**. The `data-i18n-args` attribute is **not supported by `js/i18n.js`**
(it does nothing). For dynamically-interpolated labels, omit `data-i18n` entirely
and render with `tFormat`.

Fixed in `blackjack`, `memory`, `hanoi`, `lightsout`, `codebreaker`, `mario`,
`pet`, `texasholdem`, `pay`, `liveyahtzee`, `livetictactoe`.

### 3. Computed keys shown (`suggestions.cat.general`, 2026-10-24)

`scripts/test-i18n.js` only inspects **literal** `window.t('...')` calls, so a key
built at runtime slips through:

```javascript
// BROKEN in English: locales/en.json is never fetched, so the label
// painted into the <select> was "suggestions.cat.general" (screenshot
// report 2026-10-24, suggestions.html "New Suggestion" category dropdown).
let key = 'suggestions.cat.' + o.toLowerCase().replace(/ /g, '_');
op.text = window.t(key);              // no fallback -> returns the key

// CORRECT: the English label is the fallback.
op.text = window.t(key, o);
```

Fixed in `suggestions.html` (category/language dropdown in the new-suggestion
and edit-category modals, plus the list badges). Three pieces, keep them
together:

1. `categoryLabel(label, type)` always passes the English label as the `t`
   fallback.
2. `refreshCategoryLabels()` re-paints already-populated `<option>` text on
   `rekindle:i18n:ready` (never touches option *values*, so the saved category
   is safe). It also runs immediately when `window.rekindleI18nReady` is already
   true, because for English the ready event fires from a microtask **before**
   page scripts run.
3. `renderList()` re-renders on that event so badges painted pre-locale do not
   stay English for non-English users.

`refreshCategoryLabels()` also drives the `js/custom-select.js` widget, whose
`MutationObserver` watches option text and re-renders the visible list.

**Other known computed-key `window.t()` calls without fallbacks** (same bug,
not yet fixed as of 2026-10-24): `pool2p.html`, `2pconnect4.html`,
`2ptictactoe.html`, `2pbattleships.html`, `2pchess.html` (`playerName` /
`winnerKey` lookups) and `journal.html` (`mood.*` labels). Add the fallback the
same way — e.g. `window.t(pKey, player2Wins ? 'Player 2' : 'Player 1')`.

### Custom selects inside modals

`js/custom-select.js` replaces `<select>` with an inline-block widget whose
container does **not** inherit page CSS aimed at `select` (`.modal-input`). Its
width also follows the *selected* label, so it collapses to ~90px for a short
option like "General" and clips the longer ones. **Do not stretch it to
`width: 100%`** unless the design wants a full-width field — pin a comfortable
width, centre it, and let long options wrap:

```css
#modal-overlay .custom-select-container {
    display: block;
    width: 280px;          /* not 100% - see above */
    max-width: 100%;
    margin: 10px auto;
}
#modal-overlay .custom-select-trigger { width: 100%; box-sizing: border-box; }
#modal-overlay .custom-option { white-space: normal; overflow-wrap: break-word; }
#modal-overlay .custom-options { max-height: 260px; } /* 200px cut the 6th row in half */
```

280px fits every category label, including German "Zugänglichkeitsproblem", on
one line. `suggestions.html` scopes this to `#modal-overlay` and
`#edit-cat-overlay`.

## JavaScript global `t` naming conflict

Do **not** define a global `function t(key, fallback)` in page scripts.
`js/i18n.js` already exposes the translation helper as `window.t`. Because a
global `function t` declaration also attaches itself to `window.t`, it overwrites
the i18n helper and calls itself recursively, causing
`RangeError: Maximum call stack size exceeded`.

**Example of broken code (`akinator.html` before fix):**

```javascript
function t(key, fallback) {
    if (typeof window.t === 'function') {
        return window.t(key, fallback || key); // window.t is itself, infinite loop
    }
    return fallback || key;
}
```

**Fix:** use a different local name (e.g. `translate`) and call `window.t`
inside it, or call `window.t` directly with a fallback guard.

```javascript
function translate(key, fallback) {
    if (typeof window.t === 'function') {
        return window.t(key, fallback || key);
    }
    return fallback || key;
}
```

## Bluesky: dynamic UI needs a JS translation helper (2026-10-26)

`bluesky.html` is almost entirely painted from JavaScript, so `data-i18n` alone only
covers the shell. The app uses a local `bskyText(key, fallback, vars)` wrapper around
`window.t` / `window.tFormat`:

```javascript
function bskyText(key, fallback, vars) {
    if (vars && typeof window.tFormat === 'function') return window.tFormat(key, vars, fallback);
    if (typeof window.t === 'function') return window.t(key, fallback);
    return fallback;
}
```

Rules for this page:

1. Never put `data-i18n` on `#compose-title` or the post action buttons — they are
   updated from JS. Use `bskyText` and leave the English text as the markup fallback.
2. Keep the English fallback on every call. The 67 `bluesky.*` keys exist in all 10
   locale files, but an untranslated key must still render English, never the raw key.
3. `window.onload` waits for `window.rekindleI18nReady` (or the
   `rekindle:i18n:ready` event, with a 2 s timeout) before calling `app.init()`, so
   feed/search/profile strings are built with translations. Without this, a saved
   session could paint the timeline in English before the locale fetch resolves.
4. Non-English time is rendered as 24-hour `HH:MM` by `bskyFormatTime`; English keeps
   the existing 12-hour AM/PM format.

## Language registry and adding a language (2026-11-10)

`js/i18n.js` is now the single source of truth for UI languages. It exposes
`window.rekindleLanguages` **synchronously**, before the locale fetch, with:

| Helper | Purpose |
| :--- | :--- |
| `list` / `languages` | Registry metadata (`code`, `name`, `native`, `dir`) for all known languages. |
| `shipped` / `shippedLanguages()` | Codes/metadata that have real locale files. `settings.html` builds its dropdown from this. |
| `normalize(code)` | ISO base code (`pt-BR` → `pt`, `nb`/`nn` → `no`, `iw` → `he`, `in` → `id`, `fil` → `tl`). |
| `resolveAuto(countryCode, browserLang)` | Country → browser → English, but only returns **shipped** languages. |
| `current()` | The language this device should use (saved explicit choice, else Auto). |
| `direction(code)` | `ltr` / `rtl`; the loader writes it to `<html dir>`. |

The old private country/language maps in `settings.html` (two copies),
`kindlechat.html`, `neighbourhood.html` and `topics.html` are gone; those pages
call `current()`. Kindle browsers can report `navigator.language` as `en-US`
regardless of the account language, so `COUNTRY_LANGUAGE` is what makes
"Auto (Location)" work on-device.

### Add a language

1. Add metadata to `LANGUAGES` in `js/i18n.js` if the code is new:
   `{ code: 'nl', name: 'Dutch', native: 'Nederlands', dir: 'ltr' }`.
   Use `dir: 'rtl'` for Arabic, Hebrew, Persian and Urdu.
2. Add `locales/<code>.json` and `locales/privacy-<code>.json`. Copy the key set
   from `locales/en.json` / `locales/privacy-en.json`; never rename keys and
   keep every `${placeholder}` intact. English text is the per-key fallback, so
   missing keys are safe but should be reported.
3. Add the code to `SHIPPED` in `js/i18n.js`. A locale file that is not shipped
   fails `scripts/test-locales.js` (no orphan files).
4. Add country mappings to `COUNTRY_LANGUAGE` if the language should win over a
   Kindle's `en-US` browser default. Ambiguous countries are deliberately
   omitted; `CH`→`de`, `CA`→`fr` and `SG`→`zh` are the existing choices — do not
   change them without checking the old behaviour.
5. If ELD knows the language, add it to `DETECT_LANGS` in
   `scripts/build-lang-detect.js` and run `npm run build:lang`. Bump `DETECT_URL`
   in `js/post-language.js` and `js/post-language.js?v=` on the social pages, and
   extend `scripts/test-lang-detect.js`. Languages ELD lacks (`id`, `ne`, `sw`)
   need a lexicon entry in `scripts/lang-detect-entry.js` instead. The bundle is
   ~713 KB raw / ~221 KB gzip and is lazy-loaded; do not add it to a page.
   RTL works at the `dir` level but still needs a visual pass on each layout.
6. Run `node scripts/test-locales.js` (also in `npm test`). It checks registry /
   `SHIPPED` / file consistency, placeholder parity and privacy files, and
   prints per-language coverage.
7. Bump `js/i18n.js?v=` on every page when the registry changes (138 pages).
   Locale JSON URLs are not versioned; a new file is a new URL, and edits are
   covered by `_headers` (1 h) plus the per-deploy service-worker cache reset.
8. Server side: only `DETECTED_LANGUAGE_CODES` in
   `workers/rekindle-moderate/worker.js` needs the new ISO code if it is not
   already in that set (`id`, `ne` and `sw` were added for the 2026-11-10
   batch; `af`, `fil`, `mk`, `bs` and a few others are still absent). Redeploy
   that Worker after changing it. Everything else is static. Do **not** add the language to `targetLangs` in
   `workers/rekindle-translate/worker.js`: that Google fan-out is retired.

### Loader changes that came with the registry

* `locales/en.json` is never fetched (it was already skipped); the privacy page
  now fetches only `locales/privacy-en.json`, not the 191 KB `en.json` as well.
* Unshipped browser languages resolve to English instead of requesting a
  `locales/xx.json` that 404s on every navigation.
* `?lang=xx` still previews a locale before it is added to `SHIPPED`; an
  explicit query override bypasses the shipped check.

`locales/README.md` is the translator-facing version of this checklist.

## Machine-generated locale batch (2026-11-10)

The first bulk batch came from the Counter dashboard (country visits) plus the
Suggestions board. Existing locales already covered the top markets (Brazil,
US, Spain, Mexico, UK, Argentina, Australia, Germany, Canada, Chile, Italy,
France, China, Vietnam, Poland, Portugal, Russia); this batch adds the next 30:

`ar`, `bn`, `bg`, `cs`, `da`, `el`, `he`, `hi`, `hr`, `hu`, `id`, `ja`, `ko`,
`ms`, `ne`, `nl`, `no`, `ro`, `sk`, `sl`, `sr`, `sv`, `sw`, `ta`, `th`, `tl`,
`tr`, `uk`, `ur`, `zh-Hant`.

* **Why these:** Turkish (5.3k visits), Arabic (UAE/Saudi/Egypt/Morocco), the
  Philippines, India, the Netherlands, Romania, Malaysia/Indonesia, Hungary,
  Israel, Czechia, Ukraine, Thailand, Japan, the Nordics, the Balkans, Korea,
  Bangladesh, Nepal, Kenya, Pakistan and Traditional-Chinese Hong Kong/Taiwan.
  Explicit Suggestions requests covered: Tagalog (`-Oyp0fm…`), Turkish
  (`ez3Ia…`), Korean (`-Oyn6j…`), Arabic (`-Ox5SF…` comments) and Tamil
  (`HryCL…`).
* **How:** `scripts/translate-locales.js` (default Bing `ttranslatev3`, `--google`
  for gtx). Bing batches **at most 10 entries / ~800 chars** and runs 32
  requests in parallel; above ~10 entries its LLM starts leaving UI strings in
  English. Google batches ~2,600 chars but CAPTCHA-blocks the shared IP after a
  burst. `--repair` retries values that stayed English (or still contain Latin
  words for a non-Latin target), and `--individual` is the one-request-per-key
  fallback. These are development-time tools only — never call them from the
  app or `npm test`.
* **Safety:** `${placeholders}` / `{{tokens}}` are replaced with `__RKPHn__`
  tokens before translation (Google turns `${name}` into `${الاسم}`), restored
  after, and every value is rejected back to English if placeholder, HTML tag
  or `href` parity changed. Files are written only after all batches succeed.
* **Privacy is generated too, with a notice.** `privacy-<code>.json` is produced
  by the same tool in `--privacy` mode (HTML block splitting, `<code>`/`{token}`
  protection, tag/href parity). `privacy.html` shows a machine-translation
  notice on every non-English policy, and the English text remains authoritative.
  Only the English policy is human-written. `scripts/test-locales.js` still
  treats a privacy file as optional so a future language can ship UI-first.
* **`zh-Hant` is a real locale**, not a region variant: `normalizeLang()` maps
  `zh-TW`/`zh-HK`/`zh-MO`/`zh-Hant` to `zh-Hant` before the base-code split,
  and `COUNTRY_LANGUAGE` sends TW/HK there. File: `locales/zh-Hant.json`.
* **These are unreviewed machine translations** behind the existing BETA badge.
  Corrections belong in `locales/<code>.json`; rerun `test-locales` afterwards.
* **Detection (2026-11-10):** `js/lang-detect.js` now bundles ELD's ExtraSmall
  database for 36 shipped languages plus lexicon rules for Indonesian, Nepali and
  Swahili and close-pair overrides (no/da, id/ms, ro). New scripts are handled:
  Bengali/Tamil ranges, Urdu's ٹ/ڈ/ڑ/ں/ے/ہ, Ukrainian і/ї/є/ґ, Serbian ћ/ђ/љ/њ/џ,
  Nepali's distinctive Devanagari words, and Bulgarian/Serbian word lists.
  Remaining ambiguity is inherent: Indonesian–Malay and Norwegian–Danish share
  most function words; very short messages may still pick the neighbour. UI
  localization is independent of detection.
