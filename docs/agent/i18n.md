# i18n Display Bugs & the Global `t` Naming Conflict

Read this before touching `window.t()` / `window.tFormat()` calls, `data-i18n`
attributes, or anything that renders a translated label from JavaScript.
Cross-cutting loader rules (attributes, interpolation, cache busting) stay in
[AGENTS.md](../../AGENTS.md#-localization-i18njs).

## The loader in one paragraph

`js/i18n.js` defines `window.t(key, defaultText)` **synchronously** and returns
`defaultText || key`. `window.rekindleTranslations` only fills in after the async
`fetch('locales/<lang>.json')` resolves, and it fires
`document.addEventListener('rekindle:i18n:ready')` when it does. **For
`lang === 'en'` with no `data-i18n-file`, the fetch is skipped entirely** (the
loader sets `files.length = 0`) because every `data-i18n` element already carries
English copy in the markup. So in English, `window.t('some.key')` with no
fallback returns the raw key *by design*, not as a race condition.

## The three display bugs

### 1. Raw key shown (`blackjack.label.bank`, `hangman.status.guess`, …)

`window.t('some.key')` called **without a fallback** returns `defaultText || key`,
i.e. the **raw key string**. If the code then also does
`removeAttribute('data-i18n')` (a common pattern to stop the loader overwriting
dynamic text), the raw key is stuck on screen permanently.

**Fix:** always pass an English fallback as the second argument, or use
`tFormat`. The 2026-10 codemod added fallbacks to every *literal*
`window.t('key')` call in the repo; keep it that way.

### 2. Raw `${placeholder}` shown (`MODE: ${NUM}`, `Mode: ${mode}`)

Never put `data-i18n="key"` on an element whose locale value contains `${...}`
placeholders — `applyTranslations()` sets `innerText` to the **uninterpolated
template**. The `data-i18n-args` attribute is **not supported by `js/i18n.js`**
(it does nothing). For dynamically-interpolated labels, omit `data-i18n` entirely
and render with `tFormat`.

Fixed in `blackjack`, `memory`, `hanoi`, `lightsout`, `codebreaker`, `mario`,
`pet`, `texasholdem`, `pay`, `liveyahtzee`, `livetictactoe`.

### 3. Computed keys shown (`suggestions.cat.general`, 2026-10-24)

`scripts/test-i18n.js` only inspects **literal** `window.t('...')` calls, so a key
built at runtime slips through:

```javascript
// BROKEN in English: locales/en.json is never fetched, so the label
// painted into the <select> was "suggestions.cat.general" (screenshot
// report 2026-10-24, suggestions.html "New Suggestion" category dropdown).
let key = 'suggestions.cat.' + o.toLowerCase().replace(/ /g, '_');
op.text = window.t(key);              // no fallback -> returns the key

// CORRECT: the English label is the fallback.
op.text = window.t(key, o);
```

Fixed in `suggestions.html` (category/language dropdown in the new-suggestion
and edit-category modals, plus the list badges). Three pieces, keep them
together:

1. `categoryLabel(label, type)` always passes the English label as the `t`
   fallback.
2. `refreshCategoryLabels()` re-paints already-populated `<option>` text on
   `rekindle:i18n:ready` (never touches option *values*, so the saved category
   is safe). It also runs immediately when `window.rekindleI18nReady` is already
   true, because for English the ready event fires from a microtask **before**
   page scripts run.
3. `renderList()` re-renders on that event so badges painted pre-locale do not
   stay English for non-English users.

`refreshCategoryLabels()` also drives the `js/custom-select.js` widget, whose
`MutationObserver` watches option text and re-renders the visible list.

**Other known computed-key `window.t()` calls without fallbacks** (same bug,
not yet fixed as of 2026-10-24): `pool2p.html`, `2pconnect4.html`,
`2ptictactoe.html`, `2pbattleships.html`, `2pchess.html` (`playerName` /
`winnerKey` lookups) and `journal.html` (`mood.*` labels). Add the fallback the
same way — e.g. `window.t(pKey, player2Wins ? 'Player 2' : 'Player 1')`.

### Custom selects inside modals

`js/custom-select.js` replaces `<select>` with an inline-block widget whose
container does **not** inherit page CSS aimed at `select` (`.modal-input`). Its
width also follows the *selected* label, so it collapses to ~90px for a short
option like "General" and clips the longer ones. **Do not stretch it to
`width: 100%`** unless the design wants a full-width field — pin a comfortable
width, centre it, and let long options wrap:

```css
#modal-overlay .custom-select-container {
    display: block;
    width: 280px;          /* not 100% - see above */
    max-width: 100%;
    margin: 10px auto;
}
#modal-overlay .custom-select-trigger { width: 100%; box-sizing: border-box; }
#modal-overlay .custom-option { white-space: normal; overflow-wrap: break-word; }
#modal-overlay .custom-options { max-height: 260px; } /* 200px cut the 6th row in half */
```

280px fits every category label, including German "Zugänglichkeitsproblem", on
one line. `suggestions.html` scopes this to `#modal-overlay` and
`#edit-cat-overlay`.

## JavaScript global `t` naming conflict

Do **not** define a global `function t(key, fallback)` in page scripts.
`js/i18n.js` already exposes the translation helper as `window.t`. Because a
global `function t` declaration also attaches itself to `window.t`, it overwrites
the i18n helper and calls itself recursively, causing
`RangeError: Maximum call stack size exceeded`.

**Example of broken code (`akinator.html` before fix):**

```javascript
function t(key, fallback) {
    if (typeof window.t === 'function') {
        return window.t(key, fallback || key); // window.t is itself, infinite loop
    }
    return fallback || key;
}
```

**Fix:** use a different local name (e.g. `translate`) and call `window.t`
inside it, or call `window.t` directly with a fallback guard.

```javascript
function translate(key, fallback) {
    if (typeof window.t === 'function') {
        return window.t(key, fallback || key);
    }
    return fallback || key;
}
```

## Bluesky: dynamic UI needs a JS translation helper (2026-10-26)

`bluesky.html` is almost entirely painted from JavaScript, so `data-i18n` alone only
covers the shell. The app uses a local `bskyText(key, fallback, vars)` wrapper around
`window.t` / `window.tFormat`:

```javascript
function bskyText(key, fallback, vars) {
    if (vars && typeof window.tFormat === 'function') return window.tFormat(key, vars, fallback);
    if (typeof window.t === 'function') return window.t(key, fallback);
    return fallback;
}
```

Rules for this page:

1. Never put `data-i18n` on `#compose-title` or the post action buttons — they are
   updated from JS. Use `bskyText` and leave the English text as the markup fallback.
2. Keep the English fallback on every call. The 67 `bluesky.*` keys exist in all 10
   locale files, but an untranslated key must still render English, never the raw key.
3. `window.onload` waits for `window.rekindleI18nReady` (or the
   `rekindle:i18n:ready` event, with a 2 s timeout) before calling `app.init()`, so
   feed/search/profile strings are built with translations. Without this, a saved
   session could paint the timeline in English before the locale fetch resolves.
4. Non-English time is rendered as 24-hour `HH:MM` by `bskyFormatTime`; English keeps
   the existing 12-hour AM/PM format.
